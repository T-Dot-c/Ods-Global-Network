## d. Data Model Proposal (`support_requests`)

For testing purposes in PostgreSQL (minimal table columns only, per prompt instructions):

```sql
CREATE TABLE IF NOT EXISTS support_requests (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name       VARCHAR(128) NOT NULL,
    email      VARCHAR(255) NOT NULL,
    subject    VARCHAR(200) NOT NULL,
    message    TEXT NOT NULL,
    status     VARCHAR(30) NOT NULL DEFAULT 'open',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_support_requests_created ON support_requests(created_at DESC);
```

## g. Accessibility & Mobile Notes

* Form Labels: Explicit `<label>` elements associated via `htmlFor` / `id`.
* Focus Management: On submit failure, programmatic focus moves to the error banner; on submit success, focus moves to the success confirmation heading.
* Screen Readers: `aria-live="polite"` on feedback alerts.
* Mobile Layout: Form stacks in a single column on small screens (`max-width: 600px`), with large tap targets (minimum 44x44px for buttons and inputs).

## h. Support Page Question (FAQ vs Contact Form)

* **Legacy Status**: The legacy page has **BOTH** a Contact Form (lines 115–158) and a 3-item FAQ section (lines 160–169).
* **Agent Recommendation**:
  - **Recommendation: Build BOTH (Contact Form + Structured FAQ)**.
  - **Why**: 
    1. In a digital health and services marketplace, users seeking support often have common, immediate questions (e.g., appointment confirmations, cancellation terms, refund policies). An FAQ provides instant resolution without creating backend support tickets.
    2. The contact form ensures users with specific inquiries can submit a ticket directly.
    3. Building both satisfies Section 8 ("Support tickets") and Section 1 ("Zero broken pages") of `resource/KPIs & SCOPES ODS GLOBAL NET .txt`.
  - *Note*: Per instructions, this is a recommendation only. The user will make the final decision.
